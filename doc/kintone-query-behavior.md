# kintone クエリ挙動メモ（実機観察）

実 kintone のクエリ（`/k/v1/records.json?query=...`）の仕様書に載っていない、または重要な実挙動を記録する。エミュレーターで再現する際の根拠。

観察日時: 2026-04-24

## 文字列リテラル

### エスケープシーケンス

kintone 仕様書には `\"` と `\\` のみ明記されているが、実機は以下のエスケープも受け付ける:

| 記法 | 展開 |
|---|---|
| `\"` | `"` |
| `\\` | `\` |
| `\t` | タブ文字（U+0009） |
| `\n` | （観察上は LF 相当に展開される模様） |
| `\r` | （未検証、仕様上は LF と同様に想定） |

### 生制御文字の禁止

**文字列リテラル内に生のタブ / 改行 / キャリッジリターンを含めるとエラー** になる:

```
POST /k/v1/records.json?query=文字列__1行_ like "<生タブ>"
→ 400 CB_VA01 / "クエリ記法が間違っています。"
```

クライアント側で `\t` などのエスケープに変換してから送る必要がある。

### トークン間の空白

文字列リテラル**以外**の位置（フィールドコードと演算子の間など）では、以下のいずれも空白として許容される:
- 半角スペース、タブ（`\t`）
- 改行（LF, CR, CRLF）
- 全角スペース `　`（U+3000）

つまり空白の扱いは「文字列リテラル内はエラー / 外側は緩い」という非対称構造。

## 文字列比較の挙動

### `like` / `not like` は「単語検索」

仕様書にもあるが、**SQLite の LIKE `%キーワード%` とはセマンティクスが異なる**。実機は形態素解析ベースの全文インデックス検索。

```
データ: "gamma keyword"
クエリ: 文字列__1行_ like "key"     → 0 件（部分文字列では一致しない）
クエリ: 文字列__1行_ like "keyword" → 1 件（単語単位で一致）
```

ひらがな 1 文字（`"a"` など）も、検索インデックスの最小文字数を下回っていると 0 件。

→ **エミュレーターでの完全再現は困難**。現状は SQLite の LIKE `%...%` で代用しているため挙動が異なることを README・ドキュメントに明記する。

#### 実 kintone での `like` テストは flaky

実 kintone の `like` / `not like` は **全文検索インデックスをバックグラウンドで非同期に作成** するため、レコード登録直後に `like` クエリを投げてもヒットしない（0 件で返る）ことがある。特に API による一括登録は大量データをキューに積みやすく、反映までの待ち時間が読めない。

このため `createTestApp` でレコード投入直後に `like` を検証する **dualMode テストは flaky になる前提** で、本リポジトリでは `like` / `not like` の dualMode テストを意図的に置いていない。エミュレータ側の `like` 挙動はクエリパーサ／コンパイラのユニットテスト（`packages/core/tests/query/`）でのみ検証する。

参考: [kintoneの検索のしくみと注意事項 - cybozu developer network](https://cybozu.dev/ja/kintone/tips/best-practices/data-acquisition-operation/kintone-search-mechanism-and-notes/)

### 空値判定

- `is empty` / `is not empty` は MULTI_LINE_TEXT / RICH_TEXT / FILE でのみ利用可
- **空白文字・改行・タブのみの文字列も「空」扱い**（`"   "` や `"\n"` も該当）
- SINGLE_LINE_TEXT 等には `is empty` は使えない

### `in ("")` の挙動

**値を保持していない行 + 空文字を保持する行の両方にヒット**する。つまり kintone 側では「未選択 = null / 空文字 / 空配列」を同一視。

### `=` / `in` は末尾の半角スペースを無視し、先頭 64 文字で比較する（観察日: 2026-09-26）

SINGLE_LINE_TEXT / LINK と、テーブル内の SINGLE_LINE_TEXT で確認。

- **末尾の半角スペースは、レコード値とクエリ値の両方で無視される**。`t = "abc"` / `t = "abc "` / `t = "abc  "` はどれも、値が `"abc"` / `"abc "` / `"abc  "` のレコードに一致する。`!=` / `not in` からは外れる
- 先頭の空白、末尾の全角スペース、末尾のタブは区別される（`"abc\u3000"` や `"abc\t"` は `= "abc"` に一致しない）
- **`=` / `!=` / `in` / `not in` は先頭 64 文字までしか比較しない**（ヘルプ「［＝（等しい）］を使用する場合の注意事項」の仕様が API でも同じ）。`"x"×64 + "A"` と `"x"×64 + "B"` のレコードは、`= "x"×64`、`= "x"×64 + "C"`、`in ("x"×64 + "Z")` のどれにも一致する
- 値を送らずに作ったレコードの LINK は `= ""` に一致する（空文字と同じ扱い）
- 書き込み時は末尾スペースも保存され、取得すると `"abc "` のまま返る

エミュレーターは `substr(rtrim(COALESCE(値, ''), ' '), 1, 64)` で両辺をそろえて比較する。末尾スペースの除去と 64 文字への切り詰めのどちらが先かは実機で確かめていない（64 文字目の前後に半角スペースがあるときだけ結果が変わる）。

## 数値の比較（NUMBER / CALC / RECORD_NUMBER。観察日: 2026-09-26）

出典: jibun-apps の調査（SonicGarden/jibun-apps#2806）を、`tests/api/record/records-query-compare.test.ts` の dual mode テストで再確認・補足した。

### NUMBER / CALC のクエリ値

| クエリ値 | 扱い |
|---|---|
| `05` `+5` `5e0` `5E0` `5.0` `0.5e1` `-0` `.5` | 数値に正規化して比較する。`.5` は書き込み時は 400 だがクエリでは受け付ける |
| `" 5"` `"5 "` `1,234` `5abc` `abc` | **解釈できない値**。`=` だけでなく **`!=` / `<` / `>` も 0 件**になる（`!=` は `=` の否定ではない） |
| `in` / `not in` の要素が解釈できない値 | その要素を無視する。`in ("abc")` は 0 件、`not in ("abc")` は全件 |
| `""` | `=` は未入力のレコードだけ、`!=` は入力済みのレコードだけに一致。**大小比較（`> ""` など）は `GAIA_IL08`**（「クエリの指定が不正です。」） |

**全角数字（U+FF10〜FF19）は半角と同じく数字として読む**（`= "５"` は 5 に一致、`= "1２"` は 12 に一致）。符号・小数点・指数は半角なら全角数字と組み合わせられる（`= "-１"`、`= "５e０"`）。全角の `－` `＋` `．` `ｅ`、全角スペース、U+2212 の `−` は解釈できない値になる。

書き込み時の正規化（先頭ゼロ・`+` の除去、前後空白のトリム、指数表記の展開）とは規則が違う。前後空白は書き込み時はトリムされるが、クエリでは解釈できない値になる。

### 未入力は 0 とは別の値

- `= ""` / `in ("")` にだけ一致し、`= "0"` には一致しない。`!= "0"` / `not in ("0")` には一致する
- 大小比較では -∞ 扱い。`< -1000000` / `<= -1000000` に常に一致し、`> -1000000` / `>= -1000000` には一致しない
- 値を送らずに作ったレコードも同じ扱い
- テーブル内の NUMBER も行ごとに同じ規則（`qty < -1000000` は qty が空の行を持つレコードに一致する）

### 桁数

数値精度はアプリ設定で最大 30 桁まで持てるので、倍精度浮動小数点では区別できない値がある。`n > "999999999999.9998"` は `999999999999.9999` にだけ一致する。

**クエリ値はアプリの数値精度で丸めない**（保存時は丸める。`doc/kintone-behavior-notes.md`「NUMBER の数値精度」）。既定の小数 4 桁のアプリでも、`n = "0.00015"` は保存値 `0.0002` に一致せず、`n <= "0.00015"` は `0.0002` を含まない。整数部が桁数を超えるクエリ値（`n < "1234567890123"`）もエラーにならず、そのまま比べる。そのため、`0.00015` を保存したレコードは同じ `0.00015` の `=` では見つからない（保存値は `0.0002` になっている）。

エミュレーターは SQLite 関数 `kintone_num_cmp`（`src/query/number.ts`）で 10 進数のまま比較する。引用符なしで書いた数値は lexer が JS の Number にするので、16 桁を超えると丸まる（引用符付きなら丸まらない）。

### 実機で確かめていないもの

エミュレーターは次のように扱っているが、実機の挙動は確かめていない。

- `order by`: NUMBER / CALC は従来どおり `CAST(... AS REAL)` で並べる。倍精度で区別できない近接値の順序と、未入力（0 として並ぶ）の位置は実機と違う可能性がある
- `"5."`（末尾が小数点）: 5 として解釈する
- 指数が Number で表せないほど大きい値（`1e` + 数百桁）: 解釈できない値として扱う
- NUMBER / RECORD_NUMBER に `TODAY()` などの関数を指定した場合: エラーにせず、展開した値を数値として解釈しようとする（多くは解釈できない値になり 0 件）

### RECORD_NUMBER / `$id`

- 先頭ゼロ・符号は正規化する（`= "0457"` は `= "457"` と同じ、`in` / `not in` / 大小比較も同じ）
- **NUMBER と違い、指数表記・小数表記は解釈できない値になる**（`= "462e0"` / `= "462.0"` は 0 件）
- 全角数字は NUMBER と同じく数字として読む（`$id = "＋４６２"` は 462 に一致）
- 解釈できない値に対する `!=` は 0 件（NUMBER と同じ）
- `= ""` は 0 件、`!= ""` は全件。`> ""` は `GAIA_IL08`

### エミュレーターで再現していないもの

- **アプリコードを設定したアプリのレコード番号**: 実機は `"app11-46"` の形で返し、クエリでは `"46"` でも `"app11-46"` でも一致する（SonicGarden world の調査）。エミュレーターはアプリコードを持たない
- **CALC の値そのもの**: 計算式 `n` で `n` が未入力のとき、実機の値は `""` だがエミュレーターは `"0"` になる。また `999999999999.9999` を参照すると浮動小数点で丸まる。クエリの比較規則は同じでも、保存される値が違うので結果が変わる

## 選択肢フィールド

選択肢に無い値を `in` / `not in` に指定すると、API は `GAIA_IQ10` を返す（`records-query.test.ts` の dual mode テストで確認済み。エミュレーター実装済み）。件数 0 の結果ではなくエラーになる。

## 演算子のフィールドタイプ制限

仕様書の表通りだが、不一致時のエラー形式:

```
POST /k/v1/records.json?query=ドロップダウン = "ドロップダウン1"
→ 400 GAIA_IQ03 / "ドロップダウンフィールドのフィールドタイプには演算子=を使用できません。"
```

MULTI_LINE_TEXT / RICH_TEXT で `=` を使うと同じく `GAIA_IQ03`。

## オプション

### `limit` / `offset`

- `limit`: `records.json` GET では最大 **500**。省略時 100
- `offset`: 最大 **10000**。省略時 0
- 負値は `CB_VA01`

### デフォルトの並び順

`order by` を省略した場合、**レコード番号（$id）の降順**。

### `totalCount`

GET 時に `?totalCount=true` を付けないと、レスポンスの `totalCount` は `null` として返る。付けると件数が入る。今回調べた範囲ではクエリ内の `order by` / `limit` 等とは独立した URL クエリパラメータ。

## 関数

仕様書にあるものは全て実装可。ただし以下に注意:

### `FROM_TODAY(n, UNIT)`

- 第 1 引数は必須で整数
- 第 2 引数は `DAYS` / `WEEKS` / `MONTHS` / `YEARS` のいずれか（シンボル、クォートなし）
- 引数の個数が足りないと `GAIA_IL08`、UNIT が不正だと `GAIA_IQ25`

### `THIS_WEEK(曜日)` / `LAST_WEEK` / `NEXT_WEEK`

- 曜日は `SUNDAY` ... `SATURDAY`（シンボル、クォートなし）
- 引数なしだと週全体（日〜土）

### `THIS_MONTH(...)` / `LAST_MONTH` / `NEXT_MONTH`

- 引数なし: 月全体
- `LAST` シンボル: 月末日
- 1〜31 の整数: 月内のその日
- 範囲外や無効値は `GAIA_IQ23`
- 月末の丸め: 「その月にその日が存在しなければ翌月 1 日」（例: `THIS_MONTH(31)` で 4 月 → 5 月 1 日にずれる仕様。要検証）

### `NOW()` / `TODAY()` / `YESTERDAY()` / `TOMORROW()` / `THIS_YEAR` / `LAST_YEAR` / `NEXT_YEAR`

引数なし。素直。

### タイムゾーンの影響（実機検証）

**user の「タイムゾーン」設定が日付関数の展開に使われる** 実機検証（shunichi+ai を `(UTC+13:00) サモア`、shunichi+ai-en を `(UTC-10:00) Hawaii` に設定。UTC 2026-04-24 13:51 時点で実行）:

| 関数 | Samoa user (UTC+13) | Hawaii user (UTC-10) |
|---|---|---|
| `TODAY()` | `2026-04-25` | `2026-04-24` |
| `YESTERDAY()` | `2026-04-24` | `2026-04-23` |
| `TOMORROW()` | `2026-04-26` | `2026-04-25` |
| `FROM_TODAY(0, DAYS)` | `2026-04-25` | `2026-04-24` |
| `FROM_TODAY(-1, DAYS)` | `2026-04-24` | `2026-04-23` |
| `FROM_TODAY(1, DAYS)` | `2026-04-26` | `2026-04-25` |

**user TZ 非依存**:
- `NOW()`: UTC の現在時刻に展開される。user TZ に関わらず同じ instant
- DATETIME 値の保存・返却: `2026-04-24T12:00:00Z` は user がどこの TZ でも同じ値で返る
- DATE リテラル（`d > "2026-04-01"` 等）: 保存値と比較するだけ

未検証だが TZ 依存と予想:
- `THIS_MONTH()` / `LAST_MONTH()` / `NEXT_MONTH()` / `THIS_YEAR()` 等（現在両 user とも 2026 年 4 月のため差分検出できず）

### エミュレーター実装との差分

エミュは `new Date()` でサーバー（プロセス）のローカル TZ を使うため、認証ユーザーごとに違う TODAY() を返すことはできない。実機準拠にするには `/setup/auth.json` 時に user ごとの TZ 設定を保持し、`compile` の `ExpandContext` に渡す必要がある（現状未実装）。

### `LOGINUSER()` / `PRIMARY_ORGANIZATION()`

API 呼び出し元のユーザー情報を展開する。**エミュレーターでは認証ユーザー情報をパーサーコンテキストに渡す配線が必要**（現状未実装）。

## 識別子

### フィールドコード

kintone のフィールドコード命名規則:
- 使える文字: 半角英数、半角アンダースコア、ひらがな、カタカナ、漢字、全角英数、全角記号の一部（「・」「＿」等）
- 識別子はクォート不要。**バッククォートも使えない**（実機はバッククォートを識別子クォートとして解釈しない）
- kintone 既定のシステムフィールドコード: `レコード番号` / `作成日時` / `更新日時` / `作成者` / `更新者` / `カテゴリー` / `ステータス` / `作業者`
- `$id` は「レコード番号」の別名として予約（実機でレコード番号を指すクエリで使用）

### 関連レコード / テーブル内フィールド

`関連レコード.フィールド名` 形式でネスト参照可（仕様書）。未検証。

### SUBTABLE 内フィールドのクエリ（実機観察）

app=10 の `テーブル_3` サブテーブルで検証。

#### 参照方法

**フィールドコード単独**で参照する（テーブル名プレフィックス不要）:

```
文字列1行table in ("row1-a")    # OK
テーブル_3.文字列1行table in (...) # GAIA_IR02（ドット記法は関連レコード一覧専用）
```

#### 許可演算子

- **`=` / `!=` は常に禁止**（フィールド型問わず） → `GAIA_IQ07 / テーブルに設定している場合、<code>フィールドのフィールドタイプには、演算子=を使用できません。`
- **その他の演算子**（`in` / `not in` / `>` / `<` / `>=` / `<=` / `like` / `not like` / `is empty` / `is not empty`）はフィールド型が対応していれば使える
  - NUMBER / DATE / DATETIME / TIME で `>` / `>=` など数値・日時比較も動く（仕様書の記述と異なる実挙動）

#### 行マッチング・セマンティクス

| 演算子種別 | 意味 |
|---|---|
| positive（`in` / `like` / `>` / `<` / `>=` / `<=` / `is empty`） | **少なくとも 1 行がマッチするレコード**を返す |
| negative（`not in` / `not like` / `is not empty`） | **行が 1 つ以上あり、かつ全行が条件を満たすレコード**を返す（空配列は除外） |
| 同一 SUBTABLE の `and` 結合 | **同一行制約**（例: `A in ("x") and B in ("y")` は同じ行に A=x かつ B=y がある行が必要） |
| top-level と SUBTABLE の混合 | 通常の論理演算 |

```
# id=35 (行1:[row1-a, 100] / 行2:[row1-b, 200])
文字列1行table in ("row1-a") and 数値table in ("100") → ヒット（同一行の行1）
文字列1行table in ("row1-a") and 数値table in ("200") → ヒットせず（別の行）
```

- サブテーブルが空配列のレコードは、**positive / negative どちらのクエリでもヒットしない**
  - positive（`in ("x")` / `like` / `>` など）: 行が 1 つも無いので「少なくとも 1 行がマッチ」を満たせずヒット対象外
  - negative（`not in ("x")` / `is not empty` など）: 「全行が条件を満たす」は空集合に対して真（vacuous truth）になりそうだが、実機は空配列をヒット対象外として扱う（`in ("")` でさえもヒットしない挙動と一貫）
